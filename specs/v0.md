# v0

> Or, how to host a bot?

Solution modulaire multi-couches pour héberger un assistant IA complet : modèles locaux, proxy LLM, outils MCP, workspace et interfaces utilisateur — le tout orchestré depuis un simple script shell.

## Architecture

### **renderer**

- le renderer est le moteur de rendu des fichiers d'exécutions de chaque élément de la stack
- il applique techniquement des opérations de manipulation de fichiers de code sources pour les transformer en version exécutable techniquement par le programme adapté, dans son environnement d'exécution formel (templating bash, yaml, json, etc.)

### **recette**

- une **recette** est un modèle de réalisation à appliquer avec une configuration donnée pour produire une somme de fichiers rendant exécutable une couche ou une stack.
- une **recette** est composée de :
    - un modèle composable de fichiers de descriptions d'infrastructure (.tf, docker-compose ...)
    - des modèles de scripts représentant les verbes d'actions (provision, unprovision, healthcheck, etc.)
    - un modèle de configuration qui applique les valeurs de configuration à la recette pour produire les fichiers d'exécution de la couche ou de la stack.
- ces modèles sont transformés en fichiers d'exécution par le **renderer** en appliquant les valeurs de configuration à la recette.

### **plan**

- un **plan** est un enchaînement de **recettes** qui conduit à produire une sortie composée de :
    - la description de l'infrastructure souhaitée pour l'exécution de cette couche (docker compose, dockerfile, helm, terraform, etc.)
    - ses verbes d'actions :
        - provision.sh (terraform apply, helm install, docker compose up, etc.)
        - unprovision.sh (terraform destroy, helm uninstall, docker compose down, etc.)
        - healthcheck.sh (curl, kubectl, docker ps, etc.)
        - etc.
    - une configuration par défaut de variables utilisables pour les scripts d'applications

### **layers**

- chaque **layer** possède plusieurs **plans** qui sont des variantes de la même couche avec des choix techniques différents (ex: layer "proxy-llm" avec un plan "local" utilisant llama.cpp et un plan "cloud" utilisant vertex ai)

### **stack**

- un **stack** est une composition de couches représentant une solution complète (ex: local-offgrid, cloudwrksts-vertex-ai, etc.)
- la construction d'une **stack** se fait en listant, dans un ordre d'exécutions (indice numérique pour la parallélisation), les layers en fournissant en entrée :
    - le ou les **plans** à adopter pour chaque layer
    - les valeurs de configuration à appliquer pour chaque layer si elles sont différentes de la configuration par défaut

## Choix techniques

- **renderer** : un moteur de templating simple utilisant la libraire github.com/tuxounet/k2 pour transformer les recettes en fichiers d'exécution.
- **recette** : fichiers de templates utilisant Go templating pour la génération de fichiers d'exécution à être transformés par le renderer en proposant des paramètres de configuration de la recette.
- **layers** : chaque layer est un dossier contenant plusieurs plans (sous-dossiers), chaque plan contenant les fichiers de templates de la recette et une configuration par défaut.
- **stack** : un fichier de configuration listant les layers et les plans à utiliser pour chaque layer, ainsi que les valeurs de configuration spécifiques pour chaque layer si nécessaire.
