# K-anIssA — Spécification v1

> Ajout du mode debug, de la commande `run` pour exécuter un verbe spécifique sur un plan d'un layer, et du support multi-recettes (docker-compose et shell-script).

---

## Changements par rapport à v0

### Résumé

- **Ajout** : Mode debug activable via le flag `--debug` ou la variable d'environnement `ANISSA_DEBUG=1`.
- **Ajout** : Fonction `log_debug()` dans `anissa/lib/logging.sh`.
- **Ajout** : Support du flag `DEBUG=1` dans le `Makefile` racine.
- **Ajout** : Commande `anissa run <stack> <layer> [verb] [args...]` pour exécuter un verbe spécifique sur un plan.
- **Ajout** : Fonctions `layer_run_verb()` et `layer_list_verbs()` dans `anissa/lib/layers.sh`.
- **Ajout** : Target `make run` dans le `Makefile` racine.
- **Ajout** : Support des recettes shell-script — les plans sans `compose.yml` mais disposant de `verbs/up.sh` sont désormais exécutés via leurs scripts shell au lieu d'être ignorés.
- **Ajout** : Fonction `layer_detect_type()` dans `anissa/lib/layers.sh` pour la détection automatique du type de recette.
- **Modification** : `layer_start()`, `layer_stop()`, `layer_status()`, `layer_logs()`, `layer_healthcheck()`, `layer_shell()` — toutes dispatchent désormais en fonction du type de recette détecté.
- **Modification** : `layer_start()` et `layer_stop()` pour les recettes `shell` exécutent les scripts directement (sans capture dans un subshell) — stdin, stdout et stderr sont transmis au terminal, ce qui permet les commandes interactives et l'affichage en temps réel.
- **Modification** : Aide CLI mise à jour avec la documentation du flag `--debug` et de la commande `run`.

### Justification

Le CLI v0 masque par défaut la sortie Docker pour rester lisible (cf. §5.2.6 de v0). Cependant, en cas de problème, l'utilisateur n'a aucun moyen de voir les détails d'exécution internes (résolution de chemins, variables exportées, commandes Docker exécutées, contenu des hooks, rendering k2). Le mode debug comble ce manque en fournissant un niveau de verbosité supplémentaire, activable à la demande.

De plus, le CLI v0 ne permet d'exécuter les verbes que dans le cadre d'une opération globale sur la stack (`up`, `down`, etc.). L'ajout de la commande `run` permet d'exécuter un verbe spécifique (`up.sh`, `down.sh`, `logs.sh`, `shell.sh`, ou tout verbe custom) directement sur un plan donné d'un layer, sans affecter les autres layers de la stack. Cela offre un contrôle granulaire utile pour le debug, la maintenance et le développement de layers individuelles.

### Impact sur v0

Aucun changement de comportement par défaut. Le mode debug est **désactivé** par défaut (`ANISSA_DEBUG=0`). La commande `run` est un ajout pur sans impact sur les commandes existantes. Le support multi-recettes corrige le comportement des plans shell-script qui étaient précédemment ignorés avec le message « compose.yml manquant ». Les plans docker-compose existants ne sont pas affectés. Toutes les fonctionnalités v0 restent identiques.

## 1. Mode debug — Spécification

### 1.1 Activation

Le mode debug peut être activé de deux façons (combinables) :

| Méthode                                   | Exemple                             | Portée                         |
| ----------------------------------------- | ----------------------------------- | ------------------------------ |
| Flag CLI `--debug`                        | `anissa --debug up off-grid`        | Invocation courante uniquement |
| Variable d'environnement `ANISSA_DEBUG=1` | `ANISSA_DEBUG=1 anissa up off-grid` | Session/invocation courante    |
| Variable dans `.env`                      | `ANISSA_DEBUG=1` dans `.env`        | Toutes les invocations         |
| Flag Makefile `DEBUG=1`                   | `make up DEBUG=1`                   | Invocation make courante       |

**Priorité** : Le flag `--debug` force `ANISSA_DEBUG=1` indépendamment de la variable d'environnement.

**Position du flag** : Le flag `--debug` doit être placé **avant la commande** :

```bash
anissa --debug up off-grid     # ✓ correct
anissa up --debug off-grid     # ✗ non reconnu
```

### 1.2 Fonction `log_debug()`

Ajoutée dans `anissa/lib/logging.sh` :

```bash
# Log de débogage (DIM + CYAN icône, uniquement si ANISSA_DEBUG=1)
log_debug() {
  if [[ "${ANISSA_DEBUG:-0}" == "1" ]]; then
    echo -e "${DIM}${CYAN}🔍${RESET} ${DIM}$*${RESET}"
  fi
}
```

**Comportement** :

- Ne produit aucune sortie si `ANISSA_DEBUG` n'est pas `1`.
- Utilise le style `DIM` pour se distinguer visuellement des logs normaux.
- Préfixée par l'icône 🔍 pour identification rapide.

### 1.3 Informations affichées en mode debug

Le mode debug ajoute des logs aux points suivants de l'exécution :

| Phase                    | Informations affichées                                                                                 |
| ------------------------ | ------------------------------------------------------------------------------------------------------ |
| **Démarrage CLI**        | Confirmation du mode debug, valeurs de `ANISSA_ROOT`, `ANISSA_DATA`, `ANISSA_NETWORK`, arguments reçus |
| **Chargement .env**      | Chemin du fichier `.env` chargé (ou absence)                                                           |
| **Parsing de stack**     | Chemin du fichier stack YAML, variables globales exportées, layers parsées (path + plan)               |
| **Export env layer**     | Variables d'environnement exportées pour chaque layer, chargement de `defaults.env`                    |
| **Résolution de chemin** | Chemin résolu pour chaque plan (`layer_resolve_path`)                                                  |
| **Rendering k2**         | Chemin du binaire k2 utilisé, commande exécutée, output du rendering                                   |
| **Réseau Docker**        | Vérification/création du réseau                                                                        |
| **Docker Compose**       | Commande `docker compose` complète exécutée pour chaque opération                                      |
| **Hooks**                | Contenu du hook extrait du `k2.apply.yaml` avant exécution                                             |
| **Start/Stop**           | Commande Docker Compose exécutée dans chaque plan                                                      |

### 1.5 Makefile — Support du flag DEBUG

Le `Makefile` racine supporte le flag `DEBUG=1` :

```makefile
DEBUG ?=
_DEBUG_FLAG := $(if $(filter 1,$(DEBUG)),--debug,)

up:
	@./anissa/bin/anissa $(_DEBUG_FLAG) up $(STACK)
```

**Utilisation** :

```bash
make up DEBUG=1                # Mode debug
make up DEBUG=1 STACK=lab      # Mode debug sur une stack spécifique
make up                        # Mode normal (pas de debug)
```

### 1.6 Variable réservée

| Variable       | Défaut | Description                                                                             |
| -------------- | ------ | --------------------------------------------------------------------------------------- |
| `ANISSA_DEBUG` | `0`    | Active le mode debug si définie à `1`. Affiche les détails d'exécution internes du CLI. |

```

  Variables d'environnement :
    ANISSA_DEBUG=1            Activer le mode debug via variable
```

## 2. Commande `run` — Exécution de verbe sur un plan

### 2.1 Objectif

Permettre l'exécution ciblée d'un verbe (script shell généré par la recette) sur un plan spécifique d'un layer d'une stack, sans démarrer ni arrêter les autres layers.

### 2.2 Syntaxe

```bash
anissa run <stack> <layer> [verb] [args...]
```

| Argument    | Obligatoire | Description                                                                              |
| ----------- | ----------- | ---------------------------------------------------------------------------------------- |
| `<stack>`   | Oui         | Nom de la stack (sans `.yaml`), utilisée pour résoudre la layer et charger les variables |
| `<layer>`   | Oui         | Identifiant de la layer — match partiel sur `layer_ref`, `plan` ou `layer_path/plan`     |
| `[verb]`    | Non         | Nom du verbe à exécuter (sans `.sh`). Si omis, liste les verbes disponibles              |
| `[args...]` | Non         | Arguments supplémentaires passés au script du verbe                                      |

### 2.3 Résolution de la layer

La layer est recherchée par **match partiel** (même logique que `logs` et `shell` en v0) sur :

1. La référence `layer_ref` (ex: `2.locals-subscriptions/ollama-registry`)
2. Le nom du plan seul (ex: `ollama-registry`)
3. Le chemin complet `layer_path/plan` (ex: `layers/2.locals-subscriptions/ollama-registry`)

Si aucune layer ne correspond, une erreur fatale est levée.

### 2.4 Résolution du verbe

Le verbe correspond à un fichier `verbs/<verb>.sh` dans le dossier du plan résolu. Les verbes sont les scripts shell générés automatiquement par k2 lors du rendering de la recette.

**Verbes standard** (générés par la recette `docker-compose`) :

| Verbe   | Script           | Action                                          |
| ------- | ---------------- | ----------------------------------------------- |
| `up`    | `verbs/up.sh`    | `docker compose up -d --build --remove-orphans` |
| `down`  | `verbs/down.sh`  | `docker compose down`                           |
| `logs`  | `verbs/logs.sh`  | `docker compose logs -f`                        |
| `shell` | `verbs/shell.sh` | `docker exec -it <container> bash`              |

Les recettes peuvent définir des verbes supplémentaires (verbes custom). La commande `run` exécute n'importe quel script `.sh` présent dans le dossier `verbs/`.

### 2.5 Algorithme de `anissa run`

```
1. Charger .env si présent
2. Parser stacks/<stack>.yaml
3. Chercher la layer par match partiel sur <layer>
4. Exporter les variables env de la layer
5. Si aucun verbe spécifié :
   a. Lister les fichiers verbs/*.sh du plan
   b. Afficher la liste et terminer
6. Si un verbe est spécifié :
   a. Exécuter k2 apply (rendering)
   b. Vérifier que verbs/<verb>.sh existe
   c. Exécuter le script dans le contexte du dossier du plan
   d. Afficher le résultat (succès / échec)
```

### 2.6 Mode listing (sans verbe)

Quand le verbe est omis, la commande affiche les verbes disponibles pour la layer ciblée :

```bash
$ anissa run off-grid llm-proxy
ℹ Verbes disponibles pour 3.proxy/llm-proxy :
    up
    down
    logs
    shell
```

### 2.7 Exemple d'exécution

```bash
# Exécuter le verbe up sur un plan spécifique
$ anissa run off-grid llm-proxy up
ℹ Exécution du verbe up sur 3.proxy/llm-proxy
✓ Verbe up terminé avec succès

# Exécuter le verbe logs sur un plan spécifique
$ anissa run off-grid ollama-registry logs

# Lister les verbes disponibles
$ anissa run off-grid llm-proxy

# Avec le mode debug
$ anissa --debug run off-grid llm-proxy up
```

### 2.8 Makefile — Support de `make run`

Le `Makefile` racine expose la target `run` avec les variables `LAYER` et `VERB` :

```makefile
LAYER ?=
VERB ?=
ARGS ?=

run:
	@./anissa/bin/anissa $(_DEBUG_FLAG) run $(STACK) $(LAYER) $(VERB) $(ARGS)
```

**Utilisation** :

```bash
make run LAYER=llm-proxy                    # Lister les verbes
make run LAYER=llm-proxy VERB=up            # Exécuter le verbe up
make run STACK=lab LAYER=ollama-registry VERB=logs  # Stack spécifique
make run LAYER=llm-proxy VERB=up DEBUG=1    # Avec debug
```

### 2.9 Fonctions ajoutées dans `anissa/lib/layers.sh`

#### `layer_list_verbs()`

```bash
# Liste les verbes disponibles pour un plan
# $1 = chemin absolu du plan
# Sortie : liste des noms de verbes (un par ligne, sans extension .sh)
layer_list_verbs() {
  local plan_dir="$1"
  local verbs_dir="${plan_dir}/verbs"
  if [[ ! -d "$verbs_dir" ]]; then return; fi
  for verb_file in "${verbs_dir}"/*.sh; do
    [[ -f "$verb_file" ]] || continue
    basename "$verb_file" .sh
  done
}
```

#### `layer_run_verb()`

```bash
# Exécute un verbe spécifique sur un plan
# $1 = chemin absolu du plan
# $2 = nom du verbe (sans .sh)
# $@ = arguments supplémentaires passés au script
# Retourne 0 en cas de succès, 1 en cas d'échec
layer_run_verb() {
  local plan_dir="$1"
  local verb_name="$2"
  shift 2
  local verb_script="${plan_dir}/verbs/${verb_name}.sh"
  if [[ ! -f "$verb_script" ]]; then
    # Affiche les verbes disponibles en cas d'erreur
    log_error "Verbe '${verb_name}' introuvable"
    return 1
  fi
  (cd "$plan_dir" && bash "$verb_script" "$@")
}
```

### 2.10 Aide CLI mise à jour

La commande `anissa help` affiche désormais :

```
  Commandes :
    ...
    run <stack> <layer> [verb]  Exécuter un verbe sur un plan
    ...

  Exemples :
    anissa run off-grid llm-proxy           # lister les verbes
    anissa run off-grid llm-proxy up        # exécuter un verbe
```

## 3. Support multi-recettes — Spécification

### 3.1 Contexte

En v0, le CLI assume que tout plan est basé sur docker-compose : chaque fonction de `layers.sh` vérifie la présence de `compose.yml` et ignore les plans qui n'en possèdent pas. Or le système de recettes k2 supporte aussi le type `shell-script` (ex: `google-adc`) qui n'a pas de `compose.yml` mais exécute des scripts shell via `verbs/up.sh` et `verbs/down.sh`.

### 3.2 Types de recettes

| Type      | Template k2                        | Fichiers générés                                                                             | Détection                                    |
| --------- | ---------------------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `compose` | `k.anissa.recettes.docker-compose` | `compose.yml`, `Makefile`, `verbs/up.sh`, `verbs/down.sh`, `verbs/logs.sh`, `verbs/shell.sh` | Présence de `compose.yml`                    |
| `shell`   | `k.anissa.recettes.shell-script`   | `Makefile`, `verbs/up.sh`, `verbs/down.sh`                                                   | Présence de `verbs/up.sh` sans `compose.yml` |
| `unknown` | —                                  | —                                                                                            | Aucun des fichiers ci-dessus                 |

**Priorité de détection** : `compose.yml` est vérifié en premier. Si absent, `verbs/up.sh` est vérifié. Si les deux sont absents, le type est `unknown` et le plan est ignoré (skip).

### 3.3 Fonction `layer_detect_type()`

Ajoutée dans `anissa/lib/layers.sh` :

```bash
# Détecte le type de recette d'un plan
# $1 = chemin absolu du plan
# Sortie : "compose" | "shell" | "unknown"
layer_detect_type() {
  local plan_dir="$1"
  if [[ -f "${plan_dir}/compose.yml" ]]; then
    echo "compose"
  elif [[ -f "${plan_dir}/verbs/up.sh" ]]; then
    echo "shell"
  else
    echo "unknown"
  fi
}
```

### 3.4 Comportement par type de recette

Chaque fonction de `layers.sh` dispatch désormais en fonction du type de recette :

#### `layer_start()`

| Type      | Comportement                                                                                                                                                                                         |
| --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `compose` | `docker compose up -d --remove-orphans` (inchangé) — sortie capturée                                                                                                                                 |
| `shell`   | Exécute `verbs/up.sh` dans le contexte du plan — **stdin/stdout/stderr transmis directement** au terminal (pas de capture en subshell). Permet les scripts interactifs et l'affichage en temps réel. |
| `unknown` | Retourne 2 (skip)                                                                                                                                                                                    |

#### `layer_stop()`

| Type      | Comportement                                                                                               |
| --------- | ---------------------------------------------------------------------------------------------------------- |
| `compose` | `docker compose down` (inchangé) — sortie capturée                                                         |
| `shell`   | Exécute `verbs/down.sh` si présent, sinon no-op — **stdin/stdout/stderr transmis directement** au terminal |
| `unknown` | Retourne 2 (skip)                                                                                          |

#### `layer_status()`

| Type      | Comportement                                               |
| --------- | ---------------------------------------------------------- |
| `compose` | `docker_get_status` → UP, DOWN, DEGRADED (inchangé)        |
| `shell`   | Retourne `SHELL` (pas d'état persistant Docker à vérifier) |
| `unknown` | Retourne `DOWN`                                            |

#### `layer_logs()`

| Type      | Comportement                                            |
| --------- | ------------------------------------------------------- |
| `compose` | `docker compose logs -f` (inchangé)                     |
| `shell`   | Exécute `verbs/logs.sh` si présent, sinon avertissement |
| `unknown` | Avertissement                                           |

#### `layer_healthcheck()`

| Type      | Comportement                                                  |
| --------- | ------------------------------------------------------------- |
| `compose` | Vérifie Docker + hook healthcheck (inchangé)                  |
| `shell`   | Exécute le hook healthcheck si défini, sinon retourne `SHELL` |
| `unknown` | Retourne `DOWN`                                               |

#### `layer_shell()`

| Type      | Comportement                                             |
| --------- | -------------------------------------------------------- |
| `compose` | `docker exec -it <service> bash` (inchangé)              |
| `shell`   | Exécute `verbs/shell.sh` si présent, sinon avertissement |
| `unknown` | Erreur                                                   |

### 3.5 Changements dans le CLI (`anissa/bin/anissa`)

#### `cmd_up` / `cmd_down`

Avant (v0) :

```
if compose.yml manquant → skip "compose.yml manquant"
```

Après (v1) :

```
type = layer_detect_type()
if type == "unknown" → skip "aucune recette détectée"
if type == "compose" → detail "docker compose up -d"
if type == "shell"   → detail "verbs/up.sh"
→ layer_start() / layer_stop() dispatch automatiquement
```

#### `cmd_logs` (mode agrégé)

Les plans `shell` avec `verbs/logs.sh` sont inclus dans l'agrégation des logs en parallèle.

#### `cmd_healthcheck`

Nouveau statut `SHELL` affiché pour les plans shell-script (marqué comme OK avec mention "script").

#### `cmd_layers`

Nouveau indicateur visuel :
| Indicateur | Signification |
|---|---|
| `●` (vert) | Plan docker-compose |
| `◆` (cyan) | Plan shell-script |
| `○` (dim) | Plan sans recette/inconnu |

### 3.6 Exemple : plan `google-adc` (shell-script)

```yaml
# k2.apply.yaml
k2:
  body:
    template:
      source: inventory
      params:
        id: k.anissa.recettes.shell-script
    vars:
      name: google-adc
      upScript: |
        ADC_SOURCE="${HOME}/.config/gcloud/application_default_credentials.json"
        # ── skip interactive login if credentials already exist ──
        if [[ -f "$ADC_SOURCE" ]]; then
          echo "[google-adc] ADC credentials already exist — skipping login."
        else
          gcloud auth application-default login
        fi
        ...
      downScript: |
        rm -f "$ADC_TARGET"
        ...
```

**Fichiers générés par k2** :

- `verbs/up.sh` — exécute `upScript` encadré par des messages `[google-adc] up...`
- `verbs/down.sh` — exécute `downScript` encadré par des messages `[google-adc] down...`
- `Makefile` — targets `up`, `down`, `render`

**Bonnes pratiques pour les `upScript` shell-script** :

- **Idempotence** : les scripts doivent être idempotents — relançables sans effet de bord. Vérifier l'état existant (fichier, credentials, service) avant d'exécuter une action potentiellement interactive ou destructive.
- **Interactivité** : grâce au passthrough stdin/stdout/stderr, les scripts `shell` peuvent inclure des commandes interactives (ex: `gcloud auth`, `ssh-keygen`, `read -p`), mais uniquement en fallback quand l'état n'est pas déjà satisfait.

**Comportement dans `anissa up`** :

```
[1/4] ▶ Démarrage de 1.cloud-subscriptions/google-adc
       ↳ verbs/up.sh
       ✓ google-adc démarré
```
