# K-anIssA — Spécification v0

> Solution modulaire multi-couches pour héberger un assistant IA complet : modèles locaux, proxy LLM, outils MCP, workspace et interfaces utilisateur — le tout orchestré depuis un script shell CLI.

---

## 1. Vue d'ensemble

### 1.1 Objectif

K-anIssA permet de composer et d'opérer des stacks d'infrastructure IA à partir de briques réutilisables (layers), chacune déclinée en variantes (plans). Le système repose sur deux phases :

1. **Rendering** : transformation de templates Go (via la librairie [k2](https://github.com/tuxounet/k2)) en fichiers exécutables (compose.yml, scripts shell).
2. **Orchestration** : exécution séquentielle des opérations sur chaque layer via un CLI bash (`anissa/bin/anissa`).

### 1.2 Scope de v0

| In scope | Out of scope (v1+) |
|---|---|
| Recette `docker-compose` uniquement | Recette `terraform-apply` |
| Orchestration séquentielle des layers | Parallélisation des layers |
| CLI bash pour l'orchestration | Réécriture du CLI en Go |
| Renderer Go via k2 | Autres moteurs de rendering |
| Verbes : `up`, `down`, `logs`, `status`, `healthcheck`, `shell` | Verbes : `provision`, `unprovision` (terraform) |

## 2. Architecture — Concepts clés

### 2.1 Recette

Une **recette** est un template réutilisable qui définit comment produire les fichiers d'exécution d'un type d'infrastructure donné.

**Responsabilité** : Fournir un modèle générique paramétrable de fichiers d'infrastructure + scripts d'action.

**Composition d'une recette** :

| Fichier | Rôle |
|---|---|
| `k2.template.yaml` | Manifeste k2 : déclare les paramètres attendus, les valeurs par défaut et le kind `template` |
| `compose.yml` | Template Go du fichier docker-compose (placeholder `{{ .composeFile }}`) |
| `Makefile` | Commandes make locales (`render`, `up`, `down`, `shell`, `logs`) |
| `verbs/up.sh` | Template Go du script de démarrage (`docker compose ... up -d --build`) |
| `verbs/down.sh` | Template Go du script d'arrêt (`docker compose ... down`) |
| `verbs/logs.sh` | Template Go du script de logs (`docker compose ... logs -f`) |
| `verbs/shell.sh` | Template Go du script shell interactif (`docker exec -it ...`) |

**Format du `k2.template.yaml`** :

```yaml
k2:
  metadata:
    id: k.anissa.recettes.<nom-recette>   # Identifiant unique référencé par les plans
    kind: "template"
  body:
    name: "<nom-recette>"
    parameters:                             # Paramètres avec valeurs par défaut
      name: "sample"                        # Nom du projet docker compose
      title: "Sample Component"             # Titre lisible
      description: "..."                    # Description
      composeFile: |                        # Contenu docker-compose par défaut
          services:
            workspace:
              build:
                context: .
              container_name: sample
              restart: unless-stopped
    scripts:
      pre: []
      nuke: []
```

**Recettes disponibles en v0** :

- `recettes/docker-compose/` — génère un projet docker-compose complet avec ses verbes.

### 2.2 Plan

Un **plan** est une application concrète d'une recette avec des paramètres spécifiques. C'est un fichier `k2.apply.yaml` qui référence une recette et fournit les valeurs de configuration pour produire les fichiers d'exécution de ce composant.

**Responsabilité** : Instancier une recette avec des valeurs concrètes (image Docker, ports, volumes, etc.).

**Format du `k2.apply.yaml`** :

```yaml
k2:
  metadata:
    id: k.apps.anissa.layers.<layer>.<plan>   # Identifiant unique du plan
    kind: template-apply
  body:
    template:
      source: inventory                         # Résolution via k2.inventory.yaml
      params:
        id: k.anissa.recettes.docker-compose    # Référence à la recette
    vars:
      name: "<nom-projet>"                      # Nom du projet docker compose
      title: "<titre>"                          # Titre lisible
      description: "<description>"              # Description
      composeFile: |                            # Contenu docker-compose spécifique
          services:
            <service>:
              image: <image>
              restart: unless-stopped
              ports:
                - "${PORT:-default}:container_port"
              volumes:
                - "${ANISSA_DATA:-.data}/<service>:/data"
              environment:
                - VAR=${ENV_VAR:-default}
              networks:
                - anissa
          networks:
            anissa:
              external: true
    hooks:                                      # Hooks lifecycle (optionnel)
      pre_start: |
        # Commandes shell exécutées avant le démarrage
      post_start: |
        # Commandes shell exécutées après le démarrage
      pre_stop: |
        # Commandes shell exécutées avant l'arrêt
      post_stop: |
        # Commandes shell exécutées après l'arrêt
```

**Résultat du rendering** : Le plan `k2.apply.yaml` + la recette produisent dans le dossier du plan :

```
layers/<N.layer>/<plan>/
├── k2.apply.yaml        # Source (non modifié)
├── compose.yml          # AUTOGENERATED — docker-compose résolu
├── Makefile             # AUTOGENERATED — commandes make
├── verbs/
│   ├── up.sh            # AUTOGENERATED — script de démarrage
│   ├── down.sh          # AUTOGENERATED — script d'arrêt
│   ├── logs.sh          # AUTOGENERATED — script de logs
│   └── shell.sh         # AUTOGENERATED — script shell interactif
├── config.yml           # (optionnel) Fichier de config applicatif (non généré)
├── Dockerfile           # (optionnel) Image custom (non généré)
├── layer.sh             # DEPRECATED — remplacé par hooks dans k2.apply.yaml
├── defaults.env         # (optionnel) Variables par défaut de la layer (non surchargeable par l'utilisateur)
└── links.env            # (optionnel) Labels et URLs d'accès pour affichage CLI
```

### 2.3 Layer

Une **layer** est une catégorie fonctionnelle contenant un ou plusieurs plans interchangeables.

**Responsabilité** : Regrouper les variantes d'un même besoin fonctionnel (ex: proxy LLM local vs. cloud).

**Convention de nommage** : `<N>.<nom-fonctionnel>/` où `N` est un indice d'ordre d'exécution.

**Layers définies en v0** :

| Layer | Description | Plans disponibles |
|---|---|---|
| `0.hosting` | Hébergement de base | _(doc only — pas de plan v0)_ |
| `1.cloud-subscriptions` | Abonnements cloud | _(doc only — pas de plan v0)_ |
| `2.locals-subscriptions` | Inférences locales | `ollama-embedded` (build custom), `ollama-registry` (image officielle) |
| `3.proxy` | Proxy/routeur LLM | `llm-proxy` (LiteLLM) |
| `4.tools` | Outils d'action | _(doc only — pas de plan v0)_ |
| `5.mcp` | Serveurs MCP | _(doc only — pas de plan v0)_ |
| `6.workspace` | Environnement de travail | `custom-workspace-in-container` |
| `10.clients` | Interfaces utilisateur | `wetty`, `open-webui`, `vscodium` |

**Structure d'un dossier layer** :

```
layers/<N>.<nom>/
├── <plan-a>/
│   ├── k2.apply.yaml
│   ├── compose.yml          # généré par k2
│   ├── verbs/               # générés par k2
│   ├── Dockerfile           # optionnel
│   ├── config.yml           # optionnel
│   └── links.env            # optionnel
├── <plan-b>/
│   └── ...
└── README.md                # Documentation de la layer (optionnel)
```

### 2.4 Stack

Une **stack** est une composition ordonnée de layers+plans formant une solution complète déployable.

**Responsabilité** : Définir quels plans activer, dans quel ordre, et avec quelles surcharges de configuration.

**Format du fichier `stacks/<nom>.yaml`** :

```yaml
version: v0

stack:
  description: "Description de la stack"       # Description lisible

  env:                                          # Variables globales de la stack (optionnel)
    ANISSA_NETWORK: anissa
    TZ: Europe/Paris

  layers:                                       # Liste ordonnée (exécution séquentielle)
    - layer: layers/2.locals-subscriptions      # Chemin relatif de la layer
      plan: ollama-registry                     # Nom du plan à utiliser
      env:                                      # Surcharges de config pour ce layer (optionnel)
        OLLAMA_PORT: "11434"
        OLLAMA_MODELS: "gemma3:270m"

    - layer: layers/3.proxy
      plan: llm-proxy
      env:
        LITELLM_PORT: "4000"
        LITELLM_MASTER_KEY: "sk-anissa-local"

    - layer: layers/6.workspace
      plan: custom-workspace-in-container

    - layer: layers/10.clients
      plan: wetty
      env:
        WETTY_PORT: "3000"
```

**Stacks disponibles en v0** :

- `off-grid.yaml` — Stack locale complète sans accès cloud
- `lab.yaml` — Stack de développement/test
- `claude-code-proxy-vertex.yaml` — Stack avec proxy vers Vertex AI

## 3. Configuration utilisateur

### 3.1 Fichier `.env` — Secrets et configuration locale

Le fichier `.env` à la racine du projet contient la configuration spécifique à l'utilisateur et à la machine. Ce fichier est **git-ignoré** (listé dans `.gitignore`) et ne doit **jamais être commité**.

**Rôle** : Stocker les secrets (clés API, tokens), les chemins locaux et les configurations spécifiques à l'environnement de l'utilisateur.

**Format** :

```env
# .env — Configuration utilisateur locale (NON COMMITÉ)

# Cloud providers — Clés d'accès aux services cloud
CLOUD_ML_REGION=europe-west1
ANTHROPIC_VERTEX_PROJECT_ID=my-gcp-project-id
VERTEX_API_KEY=sk-xxx-secret-key

# Overrides locaux optionnels
ANISSA_DATA=/mnt/data/anissa      # Chemin custom pour les données persistantes
TZ=Europe/Paris
```

**Règles** :
- Le fichier `.env` est chargé par le CLI au démarrage via `set -a; source .env; set +a`.
- Les variables définies ici peuvent être surchargées par le stack YAML.
- Ce fichier est le seul endroit où stocker des secrets (clés API, tokens d'authentification).
- Il ne doit contenir QUE des variables spécifiques à l'utilisateur/machine, PAS de configuration structurelle.

### 3.2 Fichier `.env.example` — Modèle de référence

Le fichier `.env.example` est commité dans le dépôt et sert de documentation/modèle pour les variables attendues.

**Format** :

```env
# .env.example — Copier en .env et remplir les valeurs

# Cloud providers (optionnel — uniquement pour les stacks cloud)
CLOUD_ML_REGION=
ANTHROPIC_VERTEX_PROJECT_ID=
VERTEX_API_KEY=

# Optionnel — surcharges locales
# ANISSA_DATA=           # Défaut : .data/
# TZ=                    # Défaut : Europe/Paris
```

**Règles** :
- Toujours commité, toujours à jour avec les variables utilisées par les stacks.
- Les valeurs sont vides ou commentées (jamais de secrets réels).
- Sert de guide pour l'utilisateur lors du premier setup.

### 3.3 Cascade de configuration — 3 niveaux

Les variables d'environnement se résolvent selon 3 niveaux, du moins prioritaire au plus prioritaire :

```
Niveau 1 (le moins prioritaire) : .env — secrets et config utilisateur locale
         ↓
Niveau 2 : defaults de la layer (dans les compose.yml via ${VAR:-default})
         ↓
Niveau 3 (le plus prioritaire) : surcharges dans le stack YAML (champ env par layer)
```

**Règles de résolution** :

1. Le fichier `.env` à la racine est chargé en premier (`set -a; source .env; set +a`).
2. Les valeurs par défaut dans les `compose.yml` générés utilisent la syntaxe `${VAR:-default}`.
3. Le champ `env` global du stack YAML est exporté dans l'environnement.
4. Le champ `env` de chaque layer dans le stack YAML est exporté avant l'exécution des verbes de cette layer, surchargeant toute valeur précédente.

**Ordre d'application effectif** :

```
.env (utilisateur) → stack.env (global) → stack.layers[n].env (par layer) → ${VAR:-default} (fallback compose)
```

### 3.4 Variables réservées (`ANISSA_*`)

Les variables préfixées `ANISSA_` sont réservées au framework et ont une sémantique définie :

| Variable | Défaut | Description |
|---|---|---|
| `ANISSA_ROOT` | _(auto-détecté)_ | Chemin racine du projet, résolu comme `anissa/bin/../../` (défini par le CLI, non configurable) |
| `ANISSA_LIB` | `$ANISSA_ROOT/anissa/lib` | Chemin vers les librairies bash (défini par le CLI) |
| `ANISSA_LAYERS` | `$ANISSA_ROOT/layers` | Chemin vers les layers (défini par le CLI) |
| `ANISSA_STACKS` | `$ANISSA_ROOT/stacks` | Chemin vers les stacks (défini par le CLI) |
| `ANISSA_DATA` | `$ANISSA_ROOT/.data` | Répertoire de données persistantes (configurable dans `.env`) |
| `ANISSA_NETWORK` | `anissa` | Nom du réseau Docker partagé (configurable dans `.env`) |

### 3.5 Variables applicatives

Les variables non-préfixées sont spécifiques aux layers et définies par chaque plan :

| Variable | Utilisée par | Définie dans |
|---|---|---|
| `OLLAMA_PORT`, `OLLAMA_MODELS` | `2.locals-subscriptions/*` | stack YAML ou `.env` |
| `LITELLM_PORT`, `LITELLM_MASTER_KEY` | `3.proxy/llm-proxy` | stack YAML ou `.env` |
| `WETTY_PORT`, `WETTY_SSH_HOST`, `WETTY_SSH_USER` | `10.clients/wetty` | stack YAML ou `.env` |
| `OPEN_WEBUI_PORT`, `OPEN_WEBUI_AUTH` | `10.clients/open-webui` | stack YAML ou `.env` |
| `CLOUD_ML_REGION`, `ANTHROPIC_VERTEX_PROJECT_ID`, `VERTEX_API_KEY` | `3.proxy/llm-proxy` (cloud routes) | `.env` uniquement (secrets) |

## 4. Renderer (k2)

### 4.1 Rôle

Le renderer utilise la librairie Go [k2](https://github.com/tuxounet/k2) pour transformer les templates (recettes) en fichiers exécutables dans chaque dossier de plan.

### 4.2 Fichier d'inventaire

Le fichier `k2.inventory.yaml` à la racine du projet déclare les templates et les applies :

```yaml
k2:
  metadata:
    id: k.apps.anissa
    kind: inventory
  body:
    folders:
      ignore: []
      templates:
        - "recettes/**/k2.template.yaml"    # Glob vers les recettes
      applies:
        - "layers/**/k2.apply.yaml"          # Glob vers les plans
    vars:
      name: k-anissa
      title: anIssA
```

### 4.3 Cycle de rendering

```
k2.inventory.yaml
  ├── recettes/**/k2.template.yaml   →  templates chargés en mémoire
  └── layers/**/k2.apply.yaml        →  pour chaque apply :
       1. Résoudre le template référencé (via params.id)
       2. Merger les vars du plan sur les parameters du template
       3. Appliquer Go templating sur tous les fichiers du template
       4. Écrire les fichiers rendus dans le dossier du plan
```

### 4.4 Déclenchement

Le rendering est exécuté **automatiquement avant chaque opération CLI**. Le CLI `anissa` appelle `k2 apply` avant d'exécuter les verbes.

**Commandes** :
- `k2 apply --inventory ./k2.inventory.yaml` — rendre tous les plans
- `k2 destroy --inventory ./k2.inventory.yaml` — supprimer tous les fichiers générés

## 5. CLI — `anissa/bin/anissa`

### 5.1 Rôle

Script bash principal qui orchestre les opérations sur une stack : chargement de la configuration, rendering, et exécution séquentielle des verbes sur chaque layer.

Toute la logique technique du CLI est implémentée dans le sous-dossier `anissa/` à la racine du projet :

```
anissa/
├── bin/
│   └── anissa           # Point d'entrée CLI (bash executable)
└── lib/
    ├── colors.sh        # Palette ANSI
    ├── logging.sh       # Fonctions de log
    ├── progress.sh      # Affichage de progression
    ├── docker.sh        # Utilitaires Docker
    ├── config.sh        # Parsing stacks YAML, cascade de config
    └── layers.sh        # Résolution de chemin, verbes, hooks
```

Ce dossier est **séparé des données déclaratives** (recettes, layers, stacks) qui sont à la racine. Le binaire `anissa/bin/anissa` résout automatiquement `ANISSA_ROOT` comme le parent de `anissa/` (c'est-à-dire la racine du projet) pour accéder aux layers, stacks et recettes.

Le CLI doit être **coloré, convivial et orienté progression**. L'utilisateur doit pouvoir suivre visuellement l'avancement de chaque opération sans être noyé dans les logs Docker.

### 5.2 Affichage et UX

#### 5.2.1 Palette de couleurs

Le CLI utilise les codes ANSI définis dans `anissa/lib/colors.sh` :

| Couleur | Usage |

### 5.3 Commandes

| Commande | Arguments | Description |
|---|---|---|
| `anissa up <stack>` | Nom du fichier stack (sans .yaml) | Render + démarrer toutes les layers de la stack |
| `anissa down <stack>` | Nom du fichier stack (sans .yaml) | Arrêter toutes les layers (ordre inverse) |
| `anissa restart <stack>` | Nom du fichier stack (sans .yaml) | `down` puis `up` |
| `anissa status <stack>` | Nom du fichier stack (sans .yaml) | Afficher le statut de chaque layer |
| `anissa logs <stack> [layer]` | Stack + layer optionnel | Afficher les logs (tous ou un seul) |
| `anissa healthcheck <stack>` | Nom du fichier stack (sans .yaml) | Vérifier la santé de chaque layer |
| `anissa shell <stack> <layer>` | Stack + layer | Ouvrir un shell dans le container de la layer |
| `anissa layers` | — | Lister toutes les layers disponibles |
| `anissa stacks` | — | Lister toutes les stacks disponibles |
| `anissa help` | — | Afficher l'aide |

### 5.4 Algorithme de `anissa up <stack>`

```
1. Charger .env si présent (secrets et config utilisateur)
2. Parser stacks/<stack>.yaml
3. Afficher la bannière : "anIssA ▶ up <stack> (N layers)"
4. Exporter les variables env globales de la stack
5. Exécuter k2 apply (rendering de tous les plans)
   ↳ Afficher : "↳ Rendering des templates..."
6. Créer le réseau Docker partagé "anissa" si inexistant
7. Pour chaque layer (i sur N) dans l'ordre déclaré :
   a. Afficher : "[i/N] ▶ Démarrage de <layer>/<plan>"
   b. Résoudre le chemin : layers/<layer-path>/<plan>/
   c. Vérifier que compose.yml existe (sinon afficher ⊘ skip et continuer)
   d. Exporter les variables env de cette layer
   e. Exécuter le hook pre_start si déclaré
   f. Exécuter : docker compose up -d --remove-orphans (output masqué)
   g. Exécuter le hook post_start si déclaré
   h. Afficher : "✓ <plan> démarré" (ou "✗ <plan> échoué" avec détails en DIM)
8. Afficher le résumé : "✓ Stack <stack> démarrée (N/N layers)"
9. Afficher les liens d'accès (tableau formaté depuis links.env)
```

### 5.5 Algorithme de `anissa down <stack>`

```
1. Parser stacks/<stack>.yaml
2. Afficher la bannière : "anIssA ▶ down <stack> (N layers)"
3. Construire la liste des layers en ordre INVERSE
4. Pour chaque layer (i sur N) :
   a. Afficher : "[i/N] ■ Arrêt de <layer>/<plan>"
   b. Résoudre le chemin
   c. Exécuter le hook pre_stop si déclaré
   d. Exécuter : docker compose down (output masqué)
   e. Exécuter le hook post_stop si déclaré
   f. Afficher : "✓ <plan> arrêté"
5. Afficher le résumé : "✓ Stack <stack> arrêtée"
```

### 5.6 Algorithme de `anissa healthcheck <stack>`

```
1. Parser stacks/<stack>.yaml
2. Afficher la bannière : "anIssA ▶ healthcheck <stack>"
3. Pour chaque layer (i sur N) :
   a. Afficher : "[i/N] ♥ Vérification de <layer>/<plan>"
   b. Vérifier que les containers sont running (docker compose ps)
   c. Exécuter le hook healthcheck si déclaré (curl, ping, etc.)
   d. Afficher le résultat : ✓ OK / ⚠ DEGRADED / ✗ DOWN
4. Afficher le tableau récapitulatif coloré
```

### 5.7 Système de hooks

Les hooks sont des scripts shell déclarés dans le `k2.apply.yaml` de chaque plan (champ `hooks`). Ils sont extraits par le CLI et exécutés aux moments appropriés du lifecycle.

**Hooks disponibles** :

| Hook | Moment d'exécution | Cas d'usage typique |
|---|---|---|
| `pre_start` | Avant `docker compose up` | Pull de modèles, création de volumes, vérification de prérequis |
| `post_start` | Après `docker compose up` | Attente de readiness, chargement de données initiales |
| `pre_stop` | Avant `docker compose down` | Sauvegarde de données, notification |
| `post_stop` | Après `docker compose down` | Nettoyage de fichiers temporaires |
| `healthcheck` | Durant `anissa healthcheck` | Vérification applicative (curl API, test de connexion) |

**Extraction** : Le CLI parse le YAML `k2.apply.yaml`, extrait les blocs hooks, et les exécute via `bash -c "$hook_content"` avec l'environnement complet (variables résolues + `ANISSA_*`).

## 6. Makefile racine — Point d'entrée utilisateur

Le `Makefile` à la racine du projet est le **point d'entrée principal** pour l'utilisateur. Chaque target appelle `./anissa/bin/anissa` avec les arguments appropriés. La stack par défaut est configurable.

**Format** :

```makefile
STACK ?= off-grid                      # Stack par défaut, surchargeable : make up STACK=lab

up:
	@./anissa/bin/anissa up $(STACK)

down:
	@./anissa/bin/anissa down $(STACK)

restart:
	@./anissa/bin/anissa restart $(STACK)

status:
	@./anissa/bin/anissa status $(STACK)

logs:
	@./anissa/bin/anissa logs $(STACK)

healthcheck:
	@./anissa/bin/anissa healthcheck $(STACK)

shell:
	@./anissa/bin/anissa shell $(STACK)

stacks:
	@./anissa/bin/anissa stacks

layers:
	@./anissa/bin/anissa layers

setup:
	$(MAKE) -C ./renderer setup

render:
	$(shell go env GOPATH)/bin/k2 apply --inventory ./k2.inventory.yaml

unrender:
	$(shell go env GOPATH)/bin/k2 destroy --inventory ./k2.inventory.yaml
```

**Utilisation** :

```bash
make up                    # Démarre la stack par défaut (off-grid)
make up STACK=lab          # Démarre une stack spécifique
make down                  # Arrête la stack par défaut
make status STACK=lab      # Statut d'une stack spécifique
```

## 7. Réseau Docker

Tous les containers de la stack partagent un réseau Docker externe nommé `anissa`.

**Règles** :
- Le réseau est créé automatiquement par `anissa up` si inexistant.
- Chaque `compose.yml` généré doit déclarer le réseau comme external.
- Les services se référencent entre eux par leur nom de container (ex: `anissa-ollama`, `anissa-litellm`).
- Convention de nommage des containers : `anissa-<plan>-<service>-1`.

Le répertoire `.data/` à la racine du projet stocke les données persistantes de chaque layer.

**Convention** : Les volumes Docker pointent vers `${ANISSA_DATA:-.data}/<service>/`.

**Exemples** :
- `.data/ollama/` — modèles Ollama téléchargés

## 11. Exigences d'implémentation

### 11.1 Langages et outils

| Composant | Langage/Outil | Justification |
|---|---|---|
| Renderer | Go (via k2) | Librairie k2 pour le templating Go |
| CLI orchestrateur | Bash | Simplicité, pas de compilation, disponible partout |
| Recettes | Go templates | Syntaxe `{{ .var }}` native de k2 |
| Stacks | YAML | Lisible, standard, facilement parsé par `yq` en bash |
| Infrastructure runtime | Docker Compose | Standard de facto pour orchestration locale |

### 11.2 Dépendances externes

| Outil | Version min. | Usage |
|---|---|---|
| `docker` | 24+ | Runtime des containers |
| `docker compose` (plugin) | v2+ | Orchestration des services |
| `k2` (github.com/tuxounet/k2) | latest | Rendering des templates |
| `yq` | 4+ | Parsing YAML dans le CLI bash |
| `bash` | 5+ | CLI orchestrateur |

### 11.3 Principes

1. **Lisibilité** : Code commenté, noms explicites, fonctions courtes.
2. **Modularité** : Ajouter une layer/plan/stack ne doit pas modifier de code existant — seulement ajouter des fichiers.
3. **Idempotence** : `anissa up` peut être relancé sans effet de bord.
4. **Fail-fast** : `set -euo pipefail` dans tous les scripts. Erreur explicite si un prérequis manque.
5. **Rendering automatique** : Chaque opération CLI déclenche un re-render k2 pour garantir la cohérence.
6. **Séparation source/généré** : Les fichiers générés portent le header `## AUTOGENERATED, DO NOT EDIT THIS FILE DIRECTLY.` et sont dans le `.gitignore` si approprié.
7. **Rétro-documentation obligatoire** : Toute modification apportée au projet (ajout de layer, plan, stack, changement de comportement CLI, évolution d'une recette, etc.) **doit impérativement** être accompagnée d'une rétro-documentation du changement dans une **nouvelle version incrémentée des specs** (ex : `v1.md`, `v2.md`, …) placée dans `anissa/specs/`. Chaque version incrémentée doit documenter : les changements effectués, la justification, et l'impact sur les versions précédentes. Les specs antérieures restent inchangées et servent de référence historique.

    kind: template-apply

                - anissa
          networks:
            anissa:
              external: true
